# Catalog surface audit

## Scope and conclusion

This audit follows model rows from Hya configuration or the existing OAuth-only fetch through the backend CLI, provider router, HTTP/Compat APIs, `/tui/bootstrap`, the Rust SDK, and the TypeScript TUI. It also follows the selected model through session events, category resolution, Workflow routes, import, and login. No product files were changed.

The current implementation has two catalog authorities:

1. `hya_app::config::load` produces `ResolvedConfig.models` (`ModelEntry`) from authorized providers and their configured `models` entries.
2. `SessionEngine::provider_catalog` calls `ProviderRouter::catalog`, which projects each provider's `Provider::catalog` rows.

They agree for ordinary explicit rows in most cases, but they are not the same value or contract. The CLI consumes (1), while server catalog APIs consume (2). With no provider catalog rows, both the CLI and server APIs synthesize a row from a default/active model. The TUI then caches the server response as if it were authoritative. Startup does not fetch a provider catalog. The only current fetch is OAuth login, which persists fetched rows and writes a default model when fetch fails.

The recommended cutover is to resolve one immutable process catalog at the config/provider composition boundary before engine/server publication. Explicit Hya model entries and successful startup discovery should become provider rows in that snapshot. Every CLI/API/SDK/TUI consumer should project that same snapshot. Empty, failed, unauthorized, malformed, unsupported, or unvalidated discovery must produce no rows and must not fall back to an active/default model. Session and Workflow model assignment can retain wire-compatible unknown refs, but those refs must not feed any catalog or selector.

## Observable acceptance scenarios

1. **Explicit Hya rows are deterministic.** Given two authorized providers and non-empty Hya model lists, startup publishes exactly normalized explicit/live-verified rows. CLI, `/config/providers`, `/provider`, `/api/provider`, `/api/model`, `/tui/bootstrap`, Rust SDK, and TUI selector expose the same provider/model set and concrete reasoning-variant metadata. Duplicate/blank ids do not produce rows.
2. **Discovery runs once per backend start.** Given a credentialed Hya provider with `kind`, `base_url`, and absent/empty `models`, a stub endpoint observes one catalog request before routes are published. Starting a second backend observes a second request. The resolved rows are process-local; the Hya config file is byte-for-byte unchanged by startup discovery.
3. **Discovery uses only declared Hya auth and endpoint.** Verify endpoint URL, method, provider-specific Authorization/session headers, disabled redirects, bounded timeout/body, and no reads of Compat/OpenCode/Claude/Codex product config. A configured provider without usable Hya credentials yields no request and no rows.
4. **Every discovery failure is empty and non-synthetic.** For timeout, connection failure, 401/403, 429/5xx, malformed JSON, oversized body, unsupported provider protocol, or an empty/only-filtered result, the affected provider contributes zero rows. Other valid providers still publish. CLI/API/bootstrap do not show an active/default fallback row for the failed provider.
5. **Snapshot immutability.** After startup, changing config or endpoint response does not change a running engine's catalog. A new startup resolves the new set. Existing Bundle runtime refresh must not mutate provider rows.
6. **No synthetic health claims.** Empty catalog responses have no provider defaults/connected ids and no model DTO claiming `active`, `enabled`, or upstream health for a fabricated row. If status fields remain for compatibility, they describe only local startup resolution, not entitlement/health.
7. **Session compatibility without catalog leakage.** Persist a historical/unknown `ModelRef` and a `ModelSwitched` event; APIs round-trip it. It is absent from every catalog/selector and a turn returns the existing typed `UnknownModel` route (or category/Workflow failover where configured).
8. **TUI stale cache behavior.** Seed `model.json` with missing-provider, missing-model, deprecated, and unknown variant entries. Bootstrap with a resolved catalog; Recent/Favorite rows are hidden, invalid current selection is rejected/falls back, and variant dialog lists only metadata for the concrete selected row. With an empty catalog, the selector is empty and prompting warns rather than selecting `offline`/default.
9. **Categories do not become rows.** A category with unknown first candidate and valid fallback chooses the valid router candidate for spawn and retains existing fallback semantics; category name/candidates never appear as catalog rows. A category with no servable candidate fails through existing typed unknown behavior.
10. **Workflow routes remain request-local.** Authored and selected Workflow route metadata round-trips, unknown tail candidates are not catalog rows, and pre-stream failover/route outcome events remain unchanged for valid candidates.
11. **Import/login policy is explicit.** If Compat import remains, only an explicit import command/first-run opt-in may read it and then write Hya config; normal startup never opens those paths. OAuth login may save credentials, but a failed/empty login-time fetch does not create a discovered model row that startup trusts.
12. **`--refresh` is intentional.** Either remove the flag and update parser/help tests, or make it invoke the same declared-provider fetch with the documented mutation/snapshot semantics. It must not silently do nothing.

## Recommended cutover and compatibility risks

1. Add a provider/config composition step after Hya credentials resolve and before `SessionEngine` construction. For each configured provider: use explicit non-empty `models` according to the open trust/intersection decision; otherwise require its own endpoint/protocol and perform one bounded startup fetch. Keep fetched rows ephemeral. Construct one resolved catalog carrying provider id, concrete id, capabilities, and reasoning metadata, then construct router/provider objects and all surfaces from it.
2. Keep source ownership strict: only `config.yaml`, Hya auth material for a declared provider, and that provider's configured endpoint may contribute startup rows. Do not call `default_compat_config_path`, parse Compat/OpenCode files, inspect another product's cache/session, or infer an endpoint from another product. Treat explicit import as a separate migration policy.
3. Remove both fallback constructors: `models_cmd::model_lines` must not manufacture `hya/{fallback_model}`, and `compat::catalog::catalog_models` must return the resolved rows (possibly empty) without using `st.agent.model`. Keep agent/session metadata fallbacks only where required for wire compatibility, and clearly separate them from catalog rows.
4. Make CLI, server APIs, `/tui/bootstrap`, Rust SDK, and TUI use one row projection. Preserve provider/model aliases and variant object order, but do not let default selection, category candidates, Workflow assignments, Session events, Recent/Favorite cache, or imported rows add entries.
5. Decide offline policy explicitly. Current `DevProvider` claims any model and `offline_router` selects `offline`, but neither publishes a catalog row. The safest contract under the PRD is an empty live catalog/selector and an offline prompt notice. If product chooses a real local offline row, define it as an explicit Hya-owned local provider/model with distinct metadata, not as an arbitrary active/default fallback.
6. Keep unknown Session model wire compatibility: `switch_model`, projection, historical message DTOs, and model-ref aliases should continue to serialize. At turn admission/stream, use existing `UnknownModel` and category/Workflow fallback behavior. Do not reject historical replay merely because the current snapshot no longer contains a model.
7. Preserve reasoning variants as metadata on a base row. `provider/model#variant` is a request/session ref, not another catalog row. Normalize discovered reasoning labels against provider adapter support; malformed/unsupported metadata must not make a row visible.
8. Preserve location wrappers and native/HTTP transport behavior, but make each location's provider/model response project the process snapshot rather than re-read another config. The existing TUI `DataProvider.location.model/provider` refresh methods and legacy `sync.data.provider` should converge or have a documented single authoritative path.

Compatibility risks to account for:

- Users with only OAuth-persisted fallback/default models may see an empty catalog after upgrade until startup discovery succeeds; this is intentional fail-closed behavior but needs clear UX.
- Existing `default_model` values may be bare, stale, or no longer discovered. Preserve them for wire/session compatibility, but do not expose them as rows; define how a missing default selects no model or the first resolved row without inventing one.
- CLI scripts may depend on `models --refresh` succeeding or printing the fallback. Removing the no-op requires a deliberate CLI contract migration.
- Compat/OpenCode first-run import may be a user-visible migration path. Removing automatic import changes first-run behavior; retaining explicit import must not violate the runtime source boundary.
- Fake/Dev test providers claim arbitrary refs but have empty catalogs. Tests that construct those providers directly will need explicit catalog fixtures when asserting visible rows; routing tests should continue to use arbitrary refs only when they test unknown/fallback execution.
- Server DTO consumers may depend on `status: active`, `enabled: true`, `connected`, or provider defaults. These fields must be redefined as local resolution facts or omitted/empty when no row exists; they cannot continue to represent synthetic upstream health.
- TUI `model.json` remains backward-compatible storage, but stale entries must stay hidden. Do not delete cache entries as part of catalog resolution unless the product explicitly chooses a cache migration; hiding is the current least disruptive behavior.
- Category and Workflow configurations may refer to models not present in a newly discovered snapshot. Preserve existing request-local failover and typed errors instead of silently adding those refs to the catalog.
- OAuth catalog response schemas and provider modalities differ. A single generic parser risks showing image/video or unsupported models; provider adapters must own endpoint shape, headers, normalization, and executable-modality filtering.

## Source boundary summary

No current normal startup path reads another agent product's configuration for runtime catalog rows. The explicit readers are `config.rs::first_run_config_bootstrap`/`import_compat_models_into_config` and the Compat default-agent reader in `hya-server/src/compat/bound_agent_metadata.rs`; only the former imports model rows, and it writes Hya config. The startup discovery implementation should keep that distinction: imports are explicit migration, while the process catalog is built only from Hya-owned resolved configuration, Hya auth, and declared-provider endpoint responses.
