# Why did TUI CI fail after focused local tests passed?

**Question:** Can the complete TUI CI gate run before a push, and what did its failures uncover?

**Answer:** Yes: run `./scripts/check-tui.sh` from the repository root. It runs frozen installs, type checks and unit tests for all four Bun packages, builds hya/xtask and runs the entire browser suite with two workers. Artifacts, temporary workspaces and default browser/Bun caches live under `~/data/hya-tui-check` (override `HYA_TUI_CHECK_DIR`). Normal development uses focused specs; full-suite runs are appropriate when requested or validating broad integration.

CI run 37687679283 exposed a compact Layout pane bug omitted from the prior focused selection. Its ten rows were entirely consumed by the frame, heading, details, expanded hints and actions after adding bubble shortcuts. Footer hint height must be bounded by pane height to leave the tree/menu viewport visible; edit previews stay on one row. The existing compact layout-editor browser regression reproduces this.

The provider-error test also read its header and error from separate transient terminal frames. Poll their adjacency using one `term.lines()` snapshot instead of non-null asserting a later lookup. Keep the adjacency assertion; removing it would mask layout regressions.

The full local run also exposed a daemon-stop test race: discovery removal can precede process exit. Poll for an empty serve-process list instead of asserting immediately; a wrongly started replacement would keep the list nonempty and still fail.
